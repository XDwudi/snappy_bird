# Snappy Bird AI 协作开发手册

> 版本：v1.0 ｜ 生效日期：2026-09-12
> 本手册是全体 Agent 的统一工作准则，与《项目规范.txt》配套执行；冲突时以本手册的操作性条款为准，产品/合规条款以《项目规范.txt》为准。

---

## 1. 角色定义与子代理映射

本项目由「1 个主会话 + N 个子代理」构成 AI 开发团队：

| 角色 | 承担者 | 职责要点 |
|------|--------|----------|
| 项目管理 Agent | **主会话**（Kimi Work 主 agent） | 任务分发、上下文管理、进度跟踪、版本归档、跨角色协同；唯一有权更新 STATE.md / CHANGELOG.md |
| 产品经理 Agent | 子代理 | 需求拆解、验收标准、合规校验 |
| 游戏策划 Agent | 子代理 | 玩法/数值/关卡方案，输出 Markdown 策划案 |
| 美术设计 Agent | 子代理 | 视觉方案、素材制作、标注（Canvas 手绘风素材用代码生成时与前端协同） |
| 前端开发 Agent | 子代理（coder） | 代码实现、性能优化、bug 修复 |
| 测试验收 Agent | 子代理 | 代码审计、模拟测试、分级 Bug 报告 |
| 体验评测 Agent（"好不好玩"） | 子代理 | 运行好玩性模拟器、站在人类玩家视角评估反馈节奏与手感，输出体验报告 |

**派发纪律**：
- 重上下文工作（通读代码、审计、长文档起草、测试）一律派子代理；主会话只保留结论与决策。
- 子代理简报必须包含：角色职责、任务目标、已知信息（精确文件路径/行号）、输出格式、禁止越权范围。
- 跨角色成果变更必须经主会话评审，禁止子代理私自改动其他角色的交付物。
- 核心方案评审、版本验收、合规判定、需求变更：必须用户（人工）确认，Agent 不得自行决策。

## 2. 标准迭代流程（六阶段）

```
①需求下发 → ②方案设计 → ③方案评审 → ④开发实现 → ⑤测试验收 → ⑥归档闭环
 (主会话)   (策划/美术并行)  (用户确认)  (前端子代理)  (测试+体验子代理)  (用户终审+主会话归档)
```

1. **需求下发**：主会话在 `docs/iterations/` 建当次迭代文档（模板见 `迭代模板.md`），写明主题、范围、验收标准。
2. **方案设计**：策划/美术子代理并行出方案，写入迭代文档或独立方案文档。
3. **方案评审**：用户确认后才进入开发；评审意见记录进迭代文档。
4. **开发实现**：前端子代理按方案编码，小步提交（commit 规范见 §4）。
5. **测试验收**：测试子代理跑模拟测试 + 代码审查，体验子代理出好玩性评估；输出分级 Bug 清单（P0/P1/P2）。**P0 清零才可交付**。
6. **归档闭环**：用户终审 → 更新 README/STATE/CHANGELOG → commit + 打 tag → 迭代文档补「结果与回顾」。

## 3. 上下文保鲜机制（防溢出、防偏移）★核心

AI 长项目最大风险是上下文溢出导致方向偏移。本机制用「三层文档 + 启动协议 + 强制收尾」解决：

### 3.1 三层文档
| 层级 | 文件 | 体量 | 作用 | 更新时机 |
|------|------|------|------|----------|
| 快照层 | `docs/STATE.md` | ≤3KB | **唯一事实源**：当前版本、系统清单、已知问题、下一步优先级 | 每次迭代收尾必更新 |
| 决策层 | `docs/DECISIONS.md` | 追加式 | 记录「为什么这么改」，防止反复推翻已定结论 | 每个架构/数值决策 |
| 设计层 | `docs/开发方案_vX.X.X.md` | 完整 | 完整设计方案，按需读章节，不全文重读 | 每个版本 |

### 3.2 会话启动协议（每次新会话/新任务强制执行）
1. 主会话先读 `docs/STATE.md` + 当前迭代文档（如有）——**只读这两个**，恢复方向。
2. 需要细节时：按 STATE.md 指引读具体文件的具体章节，或派子代理探索。
3. **禁止**主会话无目标全库通读；探索、审计一律派子代理。

### 3.3 单焦点原则
- 一个迭代只做一个主题（如「v1.2.1 修复包」「v1.3.0 音效系统」）。
- 迭代文档写明范围；开发中发现范围外问题 → 记入 STATE.md 已知问题表，**不顺手改**，走变更流程。

### 3.4 强制收尾
迭代结束未更新 STATE.md / CHANGELOG.md / 未提交 git，视为**未完成**。

## 4. 版本管理

- **版本号**：`主.次.修复`（沿用规范 §6.1）。修复包 +0.0.1，新玩法模块 +0.1.0，架构大改 +1.0.0。
- **Commit 前缀**：`feat:` 新功能 ｜ `fix:` 修复 ｜ `tweak:` 数值调整 ｜ `refactor:` 重构 ｜ `docs:` 文档 ｜ `test:` 测试 ｜ `chore:` 杂项。
- **Tag**：每个交付版本打 `vX.X.X` tag，可回溯。
- **分支**：main 保持可运行；工作量 ≥半天的重构/大功能用 `feature/xxx` 分支，完成后合并。
- **归档**：每版本的方案文档、迭代文档、审计报告随代码一同入库（docs/ 全量受 git 管理）。

## 5. 测试体系（三层）

| 层 | 工具 | 运行方式 | 覆盖 |
|----|------|----------|------|
| 模拟测试 | `test/test_*.js`（Node 直跑，不依赖 wx） | `node test/test_xxx.js` | 系统逻辑、数值、触发率、难度曲线 |
| 好玩性模拟 | `test/test_gameplay_sim.js` | 脚本化玩家自动游玩 | 生存时长、反馈节奏、正反馈密度 |
| 真机验证 | 微信开发者工具 CLI | `cli preview`（预览码）/ `cli upload`（体验版） | 实机手感、性能、兼容性 |

## 6. 目录与命名约定（docs 部分）

```
docs/
├── handbook/开发手册.md        # 本文件
├── STATE.md                    # 现状快照（唯一事实源）
├── DECISIONS.md                # 决策日志
├── CHANGELOG.md                # 版本历史
├── 开发方案_vX.X.X.md           # 各版本完整方案
├── audits/审计_vX.X.X.md        # 测试/体验审计报告
└── iterations/                 # 迭代档案
    ├── 迭代模板.md
    └── 迭代_vX.X.X_主题.md
```

素材命名沿用规范 §5.2（`类型_功能.后缀`）；文档一律 Markdown，表格禁止图片化。

## 7. 质量门禁（交付前必查）

- [ ] P0 Bug 清零，P1 有明确排期
- [ ] 相关模拟测试通过
- [ ] STATE.md / CHANGELOG.md 已更新
- [ ] git 已提交，交付版本已打 tag
- [ ] 涉及手感/视觉的改动：真机预览验证过（或明确标注「待真机验证」）
